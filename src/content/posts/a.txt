Sample Application
Throughout this workshop, you'll build and evolve a customer service agent for AnyCompany Shop, a fictional online retail store that sells electronics and accessories.

The scenario
AnyCompany Shop needs an AI-powered agent that can handle common customer inquiries without routing to a human. Customers chat with the agent through a web UI and expect it to:

Look up order status, tracking numbers, and delivery estimates
Answer product and returns questions
Do light computation (for example, "total up my two orders")
You'll start with a single agent that can only look up orders, then layer on capabilities lab by lab until you have an observable, tool-using agent with sandboxed execution and per-persona authorization.

Data model
The agent's data lives in a DynamoDB table that it reads through tools.

The table holds about 500 orders spanning a year of activity, with a mix of statuses, regions, payment methods, and channels. That's enough to analyze, not just look up. Building Agents on Amazon EKS
You'll build a customer service agent for AnyCompany Shop and grow it one capability at a time. Every lab ships its complete end-state under ~/environment/modules/. You read the code, build the container image, and deploy it to the cluster that's already running.

Every model call is served by Amazon Bedrock and reaches it through the Envoy AI Gateway, a proxy running in your cluster. The agent code never speaks to Bedrock directly and never carries Bedrock credentials: it sends an ordinary chat-completions request to the gateway, and the gateway carries the AWS identity the rest of the way. That single control point is what lets you swap models (Nova, Claude) without touching agent code.

The AI Gateway
At a glance	Details
Goal	Understand what the platform team already built, and call it yourself before you write an agent against it.
Time	~10 minutes
Prerequisites	None
Every model call in this workshop is served by Amazon Bedrock, and every one of them goes through the Envoy AI Gateway running in your cluster. The platform team set that up before you arrived. Nothing in this lab asks you to deploy it, and no agent exists yet. You are going to call the gateway directly, the way any workload in the cluster would, so that the agent you build in the next lab has an endpoint you already understand.

What is already running
The gateway runs in the envoy-gateway-system namespace as a Service named ai-gateway, reachable in-cluster at http://ai-gateway.envoy-gateway-system.svc.cluster.local/v1. It is a ClusterIP Service, so it has no address outside the cluster.

kubectl get svc ai-gateway -n envoy-gateway-system
![alt text](image-14.png)
Expected output:

NAME         TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
ai-gateway   ClusterIP   10.100.45.12   <none>        80/TCP    2h
It accepts requests in two wire formats and translates both to Bedrock's Converse API: OpenAI on /v1/chat/completions and Anthropic Messages on /anthropic/v1/messages. Which one you use is a client-library decision, not a platform one. The agents in the next labs use the OpenAI format because the Strands SDK's OpenAIModel speaks it; the coding agent in the last section uses the Anthropic path because Claude Code does.

Why route model traffic through a gateway
Three reasons, and you can see all of them from the command line in a minute.

The agent holds no AWS credentials. The gateway owns the identity that reaches Bedrock, signing each request with SigV4 using a role granted through EKS Pod Identity . An agent that never holds a credential cannot leak one.

Model names stop being an application concern. Agents ask for claude-sonnet, not us.anthropic.claude-sonnet-4-5-20250929-v1:0. More on this below, because it is the part that changes how you write agent code.

There is one place to see and shape model traffic. Every model call in the cluster crosses this hop, which is where you would attach rate limits, token budgets per team, or usage accounting. This workshop does not configure those, but that single control point is why a platform team puts a gateway here rather than letting each agent dial Bedrock directly.

Compare that to the alternative: without a gateway, every agent calls Bedrock on its own, each with its own AWS credentials, its own hardcoded model ID, and no shared place to see how much any of them are spending. The gateway trades a small amount of latency (one extra network hop) for centralized identity, model naming, and visibility, which is what makes the three points above possible.

Model aliases
The gateway keeps a table of friendly names and rewrites each to a real Bedrock model id. Print it:

kubectl get aigatewayroute bedrock -n envoy-ai-gateway-system \
  -o jsonpath='{range .spec.rules[*]}{.matches[0].headers[0].value}{" -> "}{.backendRefs[0].modelNameOverride}{"\n"}{end}'

nova-lite -> us.amazon.nova-2-lite-v1:0
nova-pro -> us.amazon.nova-pro-v1:0
nova-micro -> us.amazon.nova-micro-v1:0
claude-sonnet -> us.anthropic.claude-sonnet-4-5-20250929-v1:0
claude-haiku -> us.anthropic.claude-haiku-4-5-20251001-v1:0

The left column is what agent code asks for. The right column is what Bedrock receives.

This is worth more than the keystrokes it saves. A developer writing an agent should not have to know which provider hosts a model, how that provider spells its version, or which region prefix applies. Those are platform decisions, and they change: when the platform team moves claude-sonnet from Sonnet 4.5 to the next release, they edit this table and every agent in the cluster follows. No rebuild, no redeploy, no code review.

Where aliases point in a larger deployment: inference profiles
Here each alias maps straight to a Bedrock model id. In a production deployment it would more often map to an inference profile , which is a Bedrock resource that stands in front of a model and adds two things worth having.

The first is attribution. A profile can be tagged, and Bedrock reports usage and cost against it, so "which team spent this" becomes a question with an answer. The second is permission granularity: IAM policies can name a specific inference profile, so the gateway's role can be allowed to invoke the profile that belongs to one workload without being allowed to invoke every model in the account.

The alias indirection is what makes that switch invisible. Pointing claude-sonnet at a profile instead of a model id changes one line here and nothing in any agent.

About the missing API key
The agent you build next sets api_key="not-needed". Two separate questions sit behind that.

Does the gateway need a key to reach Bedrock? No. It authenticates with its own AWS identity through Pod Identity, so there is no client key to manage or rotate.

Does the gateway check who is calling it? Not here, and that is worth knowing. Any pod in any namespace can reach that Service URL and spend Bedrock tokens; the only boundary is that the Service is ClusterIP.

What caller authentication looks like in production
The usual approach is to make each workload prove which workload it is, using credentials Kubernetes already issues.

Every pod can request a projected service account token, a short-lived JWT signed by the cluster, scoped to an audience you choose, for example ai-agents-on-eks-anycompany-shop. The gateway validates that token against the cluster's OIDC issuer and rejects anything without it. Two things follow. Only pods running under an approved service account can call the gateway at all. And because the token names the service account, every call is attributable, so per-agent budgets and rate limits become enforceable rather than aspirational.

There is a further step for user-facing agents. The chat UI in this workshop already carries the signed-in user's Cognito token through to the agent, and the Securing the agents lab uses it to authorize tool calls. The same token can ride to the model gateway, so a model call is attributable to both the workload and the person who asked for it.

You will build exactly this pattern later: the Securing the agents lab applies JWT validation and per-caller authorization to the tool gateway, which is the same mechanism described here pointed at a different hop.
What you learned
The platform team runs an Envoy AI Gateway in front of Amazon Bedrock, and it accepts both OpenAI and Anthropic request formats.
Model aliases keep provider model names out of agent code, so the platform can change models, or move to inference profiles, without touching an agent.
The gateway holds the AWS identity so agents never carry Bedrock credentials, and today it does not authenticate its callers, which is the gap a projected service account token would close.

What is the Strands SDK?
An open-source Python SDK for building agents. The LLM decides which tools to call and in what order.

How this works: the four Strands concepts you'll meet in the code
Four concepts carry the whole SDK, and you meet all of them in Step 1:

Agent: the loop that sends messages to the LLM and executes tool calls

Tools: Python functions decorated with @tool that the agent can invoke

Observability with Langfuse
At a glance	Details
Goal	Make the agent observable by sending every LLM call and tool call to Langfuse, then read a full trace of one request.
Time	~15 minutes
Prerequisites	The Building your first agent lab
The agent from the first lab is a black box. When a reply is slow or wrong, you cannot see which model call or tool invocation caused it. In this lab you instrument the agent with OpenTelemetry and read the traces in Langfuse, and you confirm that the Envoy AI Gateway adds its own span to the same trace.

The instrumentation is the portable part. The agent emits standard OpenTelemetry spans, so the same code can report to any backend that speaks OTLP. Langfuse is what this workshop points it at.

Two pieces are already running in the cluster: Langfuse itself, and a shared OpenTelemetry (OTel) Collector that every workload exports to. Have a look:

kubectl get pods,svc -n telemetry
kubectl get pods -n langfuse
![alt text](image-20.png)
The Service named agentgateway-traces-collector in the telemetry namespace is the one that matters: it listens for OTLP on port 4318, and it is the address the agent is about to export to. Nothing new gets provisioned in this lab. All you do is deploy a version of the customer agent that emits traces.

Why the tracing backend is separate from the cluster that produces the traces
Traces are usually collected centrally. One team runs the tracing backend and every other cluster reports into it, because the value of a trace comes from comparing it against everything else. In a production deployment this Langfuse would live on a management cluster, or you would point the collector at Amazon CloudWatch instead, and the agents would not change: they export OTLP to a collector and the collector decides where it goes.

That is also why the collector, not the agent, holds the Langfuse credential. One authenticated egress means one place to rotate a key, and the workloads never see it.

What changes from the first lab
The agent code is almost identical. Three things are added so traces flow:

A Langfuse client in agent.py that authenticates on startup and flushes spans after each request.
OpenTelemetry auto-instrumentation in the image. The Dockerfile launches the app with opentelemetry-instrument, which patches httpx and FastAPI with no code change. The inbound request becomes the trace root, and the outbound LLM call carries a W3C traceparent header.
Export target: the agent-config ConfigMap already sets OTEL_EXPORTER_OTLP_ENDPOINT to the shared collector and LANGFUSE_BASE_URL to the in-cluster Langfuse. The Langfuse API keys come from a separate Kubernetes Secret. The container picks all of it up with no edit.
How this works: why the gateway span joins the same trace
The traceparent header is the important part. The Envoy AI Gateway reads it on each request, so its span nests under the agent's trace instead of starting a separate one. That is how you get a single trace showing the agent, its tool call, and the gateway in one place.

The httpx auto-instrumentation adds the header on the outbound LLM call with no code in the agent. Without it, the gateway would start its own trace and you would see two disconnected traces per request instead of one.

Agent tools with MCP
At a glance	Details
Goal	Move the agent's tools out to a standalone MCP server it discovers at runtime, and route every tool call through agentgateway.
Time	~25 minutes
Prerequisites	The Building your first agent lab
So far every tool has lived inside the agent process. lookup_order is a Python function in the same container as the agent loop. That works, but it means the tool ships with the agent, only this agent can use it, and there is no central place to control who may call it. In this lab you move the tools out to a standalone MCP server that the agent discovers at runtime, and you route every tool call through agentgateway, the in-cluster proxy that later labs use to authorize calls per persona.

What is MCP?
The Model Context Protocol  is an open standard for exposing tools to agents over a network. An MCP server publishes a set of tools; an MCP client (here, the Strands agent) connects, calls list_tools to discover what is available, and invokes them by name. The agent does not import the tool code; it learns the tools at runtime from the server.

Why that matters: four things you get by moving tools onto the network
Putting the tools on the network buys four things:

Decoupled: the tool logic lives in one place, so a change ships once instead of being rolled out to every agent that embeds it. No agent is rebuilt, and no agent session restarts. The tool server also scales independently.
Discoverable: add a tool to the server and the agent picks it up on its next connect, without being told the tool exists.
Shareable: many agents can use one tool server.
A control point: because tool calls now travel over the network, a proxy in the middle (agentgateway) can see and authorize each one. That is what the Securing the agents lab builds on.
What is agentgateway?
Tool calls do not go straight from the agent to the MCP server. They go through agentgateway , an MCP gateway: a proxy that speaks the protocol, so it can see individual tools/list and tools/call operations rather than opaque HTTP bodies. That is what makes per-tool authorization possible in the next lab.

It is already running, in the agentgateway-system namespace, reachable in-cluster at agentgateway.agentgateway-system.svc.cluster.local:

kubectl get pods,svc -n agentgateway-system
![alt text](image-27.png)
Configuration is Kubernetes-native. agentgateway implements the Gateway API , so routes are ordinary HTTPRoute objects, the same kind you would write for any Gateway API implementation, pointed at an MCP-specific backend. You will apply both in Step 2.

The pattern is not unique to this product. Amazon Bedrock AgentCore Gateway  is the managed equivalent, and other proxies are adding MCP support. What carries over is the shape: put the tool calls on the network, then put a protocol-aware proxy in the path.

What changes
The agent's tools now split into two kinds: remote tools discovered over MCP, and one that stays local.

It is now built per session and forwards the signed-in user's Cognito token on its MCP calls. This is the plumbing the Securing the agents lab turns into enforcement. The "How this works" note after Step 1 walks through it.
Why search_products stays in the agent, and what it actually does
search_products is the one tool still running inside the agent process, so you can see both styles side by side in a single agent. In production it would move behind MCP as well, for the same reasons the others did.

What it does is retrieval-augmented generation (RAG): instead of relying on what the model happens to know, the agent retrieves real records and lets the model answer from those. Here the records are products.

Product search needs this because customers do not ask for a SKU. They ask for "something to cut down background noise on calls", and no keyword lookup matches that against a product named "Noise Cancelling Headphones". So the catalog is stored in Milvus , a vector database: each product description is converted to a vector that encodes its meaning, the question is converted the same way, and the search returns the nearest ones. Similar meaning, not matching words.

One honest caveat: Milvus here runs with authentication disabled, so that call is not authorized at all. Everything you are about to set up for the MCP tools (identity on the call, a proxy that checks it) has no equivalent on the Milvus path. A production deployment would enable Milvus auth and give the agent a read-only user, or put this tool behind MCP too and let the gateway police it.

How this works: forwarding the user's token per session
The MCP server sits behind agentgateway, which (in the Securing lab) authorizes each tool call by the caller's Cognito persona, so the tool call must carry the user's identity. That creates a wrinkle: Strands' MCPClient binds its auth once, when the transport connects, and binds each discovered tool to that connection. A single import-time client shared by all users could not carry a per-user token. The fix is to build the agent per session:

# server.py: extract the forwarded token, build/cache an agent per session
access_token = authorization[7:] if authorization.lower().startswith("bearer ") else None
agent = _get_session_agent(req.session_id, access_token)

# agent.py: the session's MCP client connects WITH that token
headers = {"Authorization": f"Bearer {access_token}"} if access_token else None
client = MCPClient(lambda u=url: streamablehttp_client(u, headers=headers))

In the Agent tools with MCP lab the agent started forwarding the signed-in user's Cognito token on every tool call, but nothing checked it: agentgateway routed the call and the token just rode along. Two policies at the gateway
Enforcement is two AgentgatewayPolicy objects, and neither touches the agent: mcp-authn validates the Cognito JWT on every call, and mcp-tool-authz decides which persona may call which tool. Deny-by-default does the rest.

Both live in ~/environment/modules/700-agentgateway-authz/policies/, one file per step of the arc you are about to walk. Each file is the complete state, so applying a step replaces the one before it.

How this works: what each policy attaches to and rejects
Each policy attaches to a different object and fails a call in a different way.

Authentication (mcp-authn) attaches to the agentgateway Gateway, so it applies to everything the gateway serves. A missing or invalid token is rejected with 401 before any tool logic runs:

apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: mcp-authn
  namespace: agentgateway-system
spec:
  targetRefs:
    - kind: Gateway
      name: agentgateway
      group: gateway.networking.k8s.io
  traffic:
    jwtAuthentication:
      mode: Strict            # no token, no entry
      providers:
        - issuer: __COGNITO_ISSUER__
          audiences:
            - __COGNITO_CLIENT_ID__
          jwks:
            remote:
              backendRef:     # the JWKS host as a Backend, not a bare URL
                group: agentgateway.dev
                kind: AgentgatewayBackend
                name: cognito-jwks
                namespace: agentgateway-system
                port: 443
              jwksPath: __COGNITO_JWKS_PATH__
It validates tokens against Cognito's published signing keys, which it fetches over the network. agentgateway insists that endpoint be a declared AgentgatewayBackend rather than a URL in the policy, so each file also ships one:

apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayBackend
metadata:
  name: cognito-jwks
  namespace: agentgateway-system
spec:
  static:
    host: __COGNITO_JWKS_HOST__
    port: 443
  policies:
    tls: {}                   # TLS to :443 using the system trust store
Authorization (mcp-tool-authz) attaches to the mcp-backend from the MCP lab, so it applies only to that server's tools:

apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: mcp-tool-authz
  namespace: default
spec:
  targetRefs:
    - kind: AgentgatewayBackend
      name: mcp-backend       # the backend you created in the MCP lab
      group: agentgateway.dev
  backend:
    mcp:
      authorization:
        action: Allow
        policy:
          matchExpressions:
            - 'false'         # matches nothing: Step A's deny-all
The matchExpressions list is the only thing that changes across the three steps. Everything above it stays identical, which is what makes this a policy-only exercise.

Note the action: Allow with an expression that matches nothing. That is not a contradiction: agentgateway is deny-by-default, so as soon as one Allow rule exists, any tool call not matched by a rule is refused. An Allow list that matches nothing therefore denies everything.

The __COGNITO_*__ placeholders are filled in from Terraform outputs in Step 1.
How a denial looks matters. A missing or invalid token fails at authentication with a visible 401. But a valid token whose persona lacks the right is handled differently: agentgateway hides the unauthorized tool from tools/list, so the agent never discovers it. The model then simply reports it cannot do that, rather than surfacing a 403. So the observable effect of "this persona may not use this tool" is the tool being absent from the agent's discovered tool list.

Step C: differentiate by persona
Authenticate every call and deny every tool. The authz policy's single Allow rule matches nothing ('false'), so with one rule present, deny-by-default blocks all tools even for a valid token.

render policies/step1-deny-all.yaml | kubectl apply -f -
![alt text](image-37.png)
What that YAML actually does: it sets action: Allow and gives it a matchExpressions list containing the single string 'false'. That expression evaluates to false for every tool call, so the one Allow rule never matches anything. Agents using a sandbox
At a glance	Details
Goal	Give the agent a run_python tool that writes and runs pandas over the orders in an air-gapped, single-use microVM, and render charts inline in the chat.
Time	~25 minutes
Prerequisites	The Agent tools with MCP and Securing the agents labs
The tools so far answer a fixed question: lookup_order returns one order, check_inventory checks one product. But a Sales Analyst asks open-ended questions like "chart last month's sales by region." There is no fixed tool for that. The model needs to write code, run it over many orders, and show the result.

Running model-written code is the risk this lab handles. Each execution gets its own throwaway virtual machine on EKS, created through Kata Containers : a runtime that looks like a container to Kubernetes but boots a real VM with its own kernel underneath, so a process escaping the container has escaped into a VM rather than onto the node. The VM is air-gapped, with no network and no credentials, and it is destroyed after one run. And when the analyst wants a chart, the agent renders one inline in the chat, with a collapsible dropdown showing the exact code that produced it.

Kata supports several hypervisors. This workshop configures it with Firecracker , the open-source AWS hypervisor built for exactly this shape of workload: it boots a stripped-down VM in a few hundred milliseconds, which is what makes per-execution isolation affordable. The runtime class is named kata-fc after that pairing. Swapping in a different hypervisor would be a platform change, invisible to the agent.

Prerequisites: the Agent tools with MCP and Securing the agents labs
This lab builds on two earlier labs and does not replace them. Complete both first, or the agent has nothing to connect to and no persona check to pass:

Why not just give the model the raw orders?
You could hand the model a few hundred order rows and ask it to add them up. That is slow, it burns tokens, and models are unreliable at arithmetic over long lists. Writing df.groupby('region')['total'].sum() and running it is exact and cheap. So this lab gives the agent one tool, run_python, and teaches the model to answer analytical questions by writing pandas instead of guessing.

The catch: model-written code is untrusted. You do not want it running in the agent's pod with the agent's DynamoDB credentials. So the code runs somewhere with nothing worth stealing.

The isolation model
run_python does not execute code in the agent. It calls a broker (the code-executor MCP server) that fetches a scoped slice of orders, claims a fresh kata-fc microVM, writes the rows and the generated code into it as files, runs the code, reads back the result, and destroys the microVM. Two properties make this safe: the microVM is air-gapped (no network, no credentials), and the order rows go in as a file, so the raw data never passes through the LLM.

How this works: the broker, the microVM, and the data path
Per call, the broker:

builds a scoped, parameterized DynamoDB query from validated parameters (the model picks a fiscal quarter and optional filters, never a raw query),
fetches that bounded slice of orders (the broker holds read-only creds),
claims a pre-warmed kata-fc microVM from a pool and writes the rows and the generated code into it as files,
runs the code, reads back stdout and any chart, then destroys the microVM.
The pool is why this is fast enough to sit behind a chat message: a few microVMs are kept booted and idle, so a run claims one rather than waiting for a cold start.

Two properties make this safe to run untrusted code:

The microVM is air-gapped. Its NetworkPolicy sets egress: [] and it mounts no ServiceAccount token, so even if the code tries to exfiltrate data or call AWS, there is nowhere to go and nothing to authenticate with.
The data goes in out-of-band. The order rows are written to the microVM as a file (/app/orders.json), not passed through the LLM. The model writes code against a described schema; it never sees the raw rows in its context.

How this works: keeping the chart off the LLM path
When the analyst wants a picture, the generated code saves a matplotlib figure to /app/chart.png inside the microVM. The chart then follows the same out-of-band path as the order data, so the image never enters the LLM context:

run_python → broker → microVM: the code saves /app/chart.png
broker reads the PNG back, caches it, returns a short chart_id to the agent
agent fetches the PNG from the broker (GET /chart/{id}) and streams it to the UI
UI renders the chart inline, below the collapsible code step
The model only ever sees a chart_id, never the base64 image. The bytes travel broker → agent → browser on a side channel, exactly like the order rows are injected on a side channel. This keeps the "data never passes through the LLM" property intact for the picture as well as the numbers.

Why bother: an image is expensive in tokens and useless to the model here, since it already knows what it plotted. Keeping it out of the context window costs nothing and removes an entire class of accident.

At scale, put the image in object storage instead of application memory: the broker writes the PNG to Amazon S3 and returns a presigned URL that expires in minutes. Any replica can then serve any chart, a restart loses nothing, and the browser fetches the bytes directly. The property that matters, the model seeing only a reference, is the same either way.

Here the broker keeps the bytes in a small in-memory cache, which is why the whole path fits in one file you can read.
Persona: who may run code
run_python is gated to the Sales Analyst persona. Signed in as the analyst, the tool is available; signed in as the Support Associate, the same request is denied at agentgateway (the JWT persona check from the Securing the agents lab). Code execution is a high-impact capability, so it is scoped to the role that needs it.

@mcp.tool()
def run_python(code: str, period: str, region: str | None = None, ...) -> dict:
    """Run Python against a scoped slice of the orders dataset in a microVM.
    Save a chart to /app/chart.png to show the user a figure.
    ..."""
    rows = _fetch_rows(period=period, region=region, ...)  # scoped DynamoDB Query
    result = run_in_sandbox(code, rows)                      # vend microVM, run code
    image_png = result.pop("image_png", None)
    if image_png:
        result["chart_id"] = _charts.put(image_png)          # cache; return id only
    return result
The tool returns stdout, a row count, and (if the code drew one) a chart_id. The raw PNG stays in the broker's cache. The docstring tells the model to fetch a whole fiscal quarter and filter to a month in code, so a "last month" question works against the quarter-keyed dataset.

Each execution is single-use: the broker claims a pre-warmed microVM from the kata-fc-python-pool, runs the code, and always terminates it, so nothing (files, processes, state) survives into the next run. The pool then spins up a fresh replacement.

To watch that happen you need eyes on the sandboxes before the run starts, so set up two observation terminals first. The log stream line by line
Note what the pod log does not show: the code, its stdout, or the chart. Those travel only in the request/response bodies, back through the broker into the tool result, which you saw in the Langfuse trace above. The log is just the runtime's access log, which is exactly what makes it a clean proof of the data path: code and data go in over /upload, results come out over /download, and nothing else talks to the microVM.

Finally, confirm the air gap. Read the policy itself rather than the summary table, because the rules are the interesting part:

kubectl get networkpolicy kata-fc-python-airgap -n agent-sandbox \

![alt text](image-62.png)
The part that matters:

"egress": [],
"policyTypes": ["Ingress", "Egress"]
An empty egress list with Egress in policyTypes is not "no rules configured", it is "no destination is permitted". The microVM computed your chart with nowhere to send anything. Combined with automountServiceAccountToken: false on the pod, code running in there has neither a route out nor a credential to use if it found one.

The ingress rule is equally narrow: the only thing allowed to talk to a sandbox is the sandbox router, by pod selector, so the broker's traffic can get in and nothing else can.
